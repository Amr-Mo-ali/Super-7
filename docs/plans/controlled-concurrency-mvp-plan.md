# Controlled concurrency MVP implementation plan

The default remains one active analysis until MVP-6 produces reviewed VPS evidence approving two. Each phase is independently reviewable and must preserve the documented non-durable semantics.

| Phase | Objective and likely files | Allowed / forbidden behavior | Tests and evidence before proceeding | Rollback |
|---|---|---|---|---|
| MVP-1 | Add measurement-only timing, queue-depth, active-process, callback, and cleanup observability. Likely `src/diagnostics`, `src/api/routes.py`, `src/services/analysis_queue.py`, logging tests. | Add safe logs/metrics; do not alter request schema, scoring, queue capacity, callback policy, or concurrency. | Unit tests for timing/log safety; one-process baseline logs on representative VPS videos. | Disable/remove additive instrumentation. |
| MVP-2B | Extract a pure pickle-safe child analysis entry point and composition initializer without runtime wiring. | Build fake child-owned model/pipeline state by PID; use explicit request/result contracts; no child callbacks, real YOLO in CI, network, or public API changes. | Prove exact public success/failure parity after parent conversion, pickle round trips, child ownership, and no callback in the child. | Keep the current in-process path. |
| MVP-2C | Add an experimental `ProcessPoolExecutor` runtime mode with exactly one worker. | Use explicit `spawn`; retain the bounded queue as admission; do not enable two workers or change contracts. | Verify one submission, parent callbacks, shutdown, broken-pool behavior, and in-process rollback. | Default to and retain in-process execution. |
| MVP-3 | Validate bounded behavior and prepare a controlled concurrency-two configuration, still defaulting to one. | Enable two only in controlled test configuration; do not add Redis, Celery, PostgreSQL, API fields, or unbounded queues. | Tests prove max active count, FIFO/admission behavior, 503 saturation, no accidental third process, and worker crash logging. | Set active limit to one or return to the current serial worker. |
| MVP-4 | Harden callback handoff, temporary-resource cleanup, and bounded shutdown within non-durable limits. Likely callback, lifecycle, artifact, and shutdown tests. | Move callback retry off CPU analysis occupancy if MVP-2 boundary supports it; retain current payload/attempt semantics unless explicitly approved. Do not promise recovery or exactly-once delivery. | Callback timeout/failure, queued/running shutdown, grace-period, forced-stop, and cleanup tests. | Retain inline callback behavior or default one active worker. |
| MVP-5 | Run local load and failure tests using safe fixtures. Likely integration/load scripts and tests only. | Exercise concurrency configurations; do not change production Compose, CI deployment, model/scoring formulas, or contracts. | One/two/four requests, saturation, invalid video, analysis exception, callback failure, and shutdown scenarios with collected measurements. | Discard test configuration and keep default one. |
| MVP-6 | Benchmark the actual VPS: first one process, then a controlled two-process trial. Likely operational runbook/documented evidence; no code change required unless a defect is found. | Change only temporary deployment configuration under authorized controlled testing; do not declare durability or deploy a broader topology. | Required ADR-006 measurements, host/container logs, RAM/swap/OOM review, API responsiveness, and cleanup evidence. | Restore active limit one and restart the known-good service. |
| MVP-7 | Make the documented go/no-go decision and controlled configuration rollout. Likely ADR/runbook/config documentation and narrowly scoped configuration. | Enable default two only with approved MVP-6 evidence; do not add persistence or change contracts. | Reviewed evidence meets ADR-006 qualitative rules and agreed numeric thresholds. | Immediately restore default one; preserve collected evidence for the durability decision. |

At every phase, Apex remains responsible for its own request records, unresolved-request handling, and duplicate callback tolerance. A need for restart recovery, durable acceptance, or durable callback retries stops this plan and triggers ADR-004/ADR-005 work instead.
