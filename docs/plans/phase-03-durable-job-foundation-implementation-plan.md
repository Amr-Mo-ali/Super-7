# Phase 03: Durable job foundation implementation plan

## Scope and sequencing

Implement ADR-005 in bounded, independently reviewable commits. Keep current scoring and analysis behavior unchanged; introduce the V1 job contract behind a backward-compatible migration path. PostgreSQL is Super-7-owned; no Apex tables are touched.

| Milestone | Objective and expected components | Invariants / tests | Rollback and done |
|---|---|---|---|
| 1. Dependencies and configuration | Add PostgreSQL driver, migration tooling, connection-pool settings, worker role settings, lease/poll/attempt/retention configuration, and documented secret names. Expected: `pyproject.toml`, lockfile, `src/core/config.py`, configuration tests. | No default credentials; config validates safe positive limits; existing local startup path remains explicit. Unit-test parsing/validation. | Revert dependency/config commit. Done when no runtime role uses persistence yet. |
| 2. Persistence schema/models | Define Super-7-owned job, idempotency binding, attempt, result, and callback-outbox models. Expected new persistence package and schema metadata. | Immutable request fingerprint, job/result ownership, no Apex table access. Unit-test model constraints/serialization boundaries. | No route wiring yet; migration not applied. Done when model review confirms ADR-004 fields. |
| 3. Migration setup | Add reversible development migration workflow and initial schema migration. Expected migration config/scripts and migration tests. | Separate Super-7 database/schema/user; required primary/unique/claim/lease/outbox indexes. | Downgrade tested in empty development database; production rollout requires backup. Done when fresh upgrade produces the reviewed schema. |
| 4. Repository/port interfaces | Introduce ports for acceptance, job claim, attempts, finalization, outbox, and status read; add PostgreSQL adapters. | Business flow does not depend on ORM session details; atomic methods have explicit transaction boundaries. Unit-test fake/adapter conformance. | Existing queue remains active. Done when adapters are callable only from tests. |
| 5. Atomic idempotent acceptance | Implement one transaction for immutable job, key binding, resolved version, initial `QUEUED`, and dispatch intent. Adapt V1 request/response at the API boundary. | 202 only after commit; identical concurrent requests return one job; mismatches return 409; pre-commit failure leaves no accepted job. Unit and concurrent integration tests. | Feature flag/legacy route behavior remains available during migration. Done when duplicate and timeout-retry tests pass. |
| 6. Durable dispatch intent | Persist/claim dispatch intent without a broker; add worker wake-up/poll contract. | Post-accept dispatch failure leaves a visible queued job; no contradictory 503 after acceptance. Integration-test delayed worker and API restart. | Disable worker roles while accepted jobs remain recoverable. Done when polling discovers every accepted queued job. |
| 7. Worker claim and lease | Add worker entry point and short transactional `SKIP LOCKED` (or equivalent) claim, lease token/version, and one-job concurrency. | One valid claim at a time; no transaction spans analysis; worker cannot finalize after losing fence. Concurrency and claim-race tests. | Keep worker count one until resource tests approve two. Done when two test workers cannot double-execute. |
| 8. Execution-attempt recording | Create attempt IDs/counts, started/finished timestamps, worker/lease identity, and safe classification. | Automatic retry uses same job/key/resolved version; `RUNNING → QUEUED` only for eligible bounded attempts; no intermediate callback. Unit tests for retryable/non-retryable/exhausted paths. | Disable automatic retry by configuration if needed. Done when attempt audit is queryable. |
| 9. Result finalization | Persist successful result or terminal failure with lease-fenced transition. | `COMPLETED` requires finalized successful result; terminal failure requires classification/exhaustion; one job cannot overwrite another result. Unit and database transaction tests. | Keep result retention conservative; failed finalization remains recoverable, not falsely terminal. Done when crash-point tests cover pre/post finalization. |
| 10. Callback outbox | Create callback event in the same finalization transaction; implement separate dispatcher role and durable delivery-state transitions. | Event exists only after terminal durable record; retries reuse event ID; callback failure never changes analysis result. Unit tests plus callback receiver integration tests. | Dispatcher can be stopped without losing events. Done when callback restart/redelivery is idempotent. |
| 11. Startup and lease recovery | Implement startup/periodic reconciliation for queued dispatch, expired leases, and due callbacks. | Accepted jobs survive restart; stale running work is requeued/finalized by policy; no assumed completion from memory. Crash/restart integration tests. | Run recovery in observe-only mode first if needed. Done when deterministic crash fixtures recover correctly. |
| 12. Health/readiness | Extend health with database reachability, migration compatibility, worker availability, queue capacity/backlog, and outbox age. | Readiness rejects unsafe acceptance; liveness does not hide durable backlog. Health unit/integration tests. | Preserve current route behavior until new checks are enabled deliberately. Done when outage cases are observable. |
| 13. Metrics and logging | Add structured lifecycle correlation by job/attempt/event IDs; queue depth, wait/run times, leases, retries, outbox backlog, and failures. | No raw idempotency keys/secrets/PII in logs; metrics derive from PostgreSQL source of truth. Unit tests for safe logging and metric calculations. | Metrics are additive. Done when dashboards/alerts have documented names and meanings. |
| 14. Unit-test hardening | Cover repositories, transactions, idempotency conflicts, claims, leases, retries, finalization, outbox, and migration compatibility. | Tests do not load production models or require Apex. | Keep fakes only at ports. Done when deterministic tests cover every ADR-004 transition. |
| 15. Integration tests | Exercise API acceptance, two workers, PostgreSQL, shared video references, callbacks, duplicates, and terminal metadata. | One logical job per key; result/callback separation retained. | Isolated Compose test stack. Done when tests pass without production volumes/models. |
| 16. Crash/restart tests | Inject process death after acceptance, claim, analysis, finalization boundary, callback creation, and callback attempt. | Durable recovery and event identity hold at each point. | Run only against disposable database. Done when no accepted-job-loss path remains. |
| 17. Docker Compose changes | Add Super-7 PostgreSQL, API, worker (initially one then measured two), and callback dispatcher services; volumes, health checks, secrets/configuration, and backup guidance. | Separate service roles; no Kubernetes/broker; database has durable storage; workers share read-only video/model mounts. | Compose rollback preserves database volume and uses compatibility migration procedure. Done when local/deployment Compose health passes. |
| 18. Backward-compatible migration | Release `jobId` plus equal `analysisId`, V1 keys/schema version, legacy no-key mode with explicit no-guarantee warning, then require V1 after Apex cutover. | Apex can persist job/event IDs before strict enforcement; no unsafe silent compatibility. Contract/API migration tests. | Maintain alias until verified cutover; database rollback follows migration policy. Done when legacy retirement is explicitly approved. |

## Commit grouping

1. Milestones 1–3: persistence foundation, no request-path behavior.
2. Milestones 4–6: ports plus durable acceptance, behind migration/feature control.
3. Milestones 7–9: one durable analysis worker and execution/result semantics.
4. Milestones 10–13: callback dispatcher, recovery, health, observability.
5. Milestones 14–16: adversarial unit/integration/crash verification.
6. Milestones 17–18: measured two-worker Compose rollout and Apex contract cutover.

Do not combine these groups into one implementation task. Promote from one worker to two only after the resource and crash tests demonstrate that the 4-vCPU/15-GiB VPS can sustain the selected model/video workload.
